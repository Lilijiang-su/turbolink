# TurboLink 扩容迁移（2 库 → 4 库）

## 目标

把短链系统从 **2 库 × 4 表 = 8 片** 平滑扩容到 **4 库 × 4 表 = 16 片**，采用**双写迁移**方案，全程不停服。

## 路由算法变化

| 阶段 | 库路由 | 表路由 |
|------|--------|--------|
| 旧（2库） | `db = h % 2` | `table = (h / 2) % 4` |
| 新（4库） | `db = h % 4` | `table = (h / 4) % 4` |

其中 `h = short_code.hashCode() & 0x7fffffff`（消负数哈希，正确处理 Integer.MIN_VALUE）。

## 迁移五阶段

```
① 单写旧库 → ② 开启双写 → ③ 存量搬迁 → ④ 数据校验 → ⑤ 切读 + 关旧写
```

| 阶段 | 操作 | 接口/脚本 |
|------|------|----------|
| ① 常态 | 写只落旧库（2库） | 默认 |
| ② 双写 | 写同时落旧库+新库（4库） | `POST /api/migration/dual-write/on` |
| ③ 搬迁 | 存量按新路由搬到新库（幂等） | `benchmark/MigrationScript.java` |
| ④ 校验 | 逐条比对源/目标一致性 | MigrationScript 内置 |
| ⑤ 切读 | 读切到新库，关闭双写 | `POST /api/migration/read-new/on` + `dual-write/off` |

## 关键实现

- **MigrationCoordinator**：迁移开关（dualWrite / readNew），可运行时热切换
- **MigrationTargetDataSource**：独立构建 4 库 ShardingSphere 数据源（`sharding-4db.yml`），惰性初始化 + 容错
- **MigrationScript**：存量搬迁 + 校验 + 清理残留，路由算法与 `ShardingUtil` 严格一致

## 迁移中发现的 2 个真实工程问题

### 1. 双写主键冲突（经典坑）

**现象**：双写期间，某短码的旧路由（`h%2`）和新路由（`h%4`）可能落在**同一物理库表**，主库插入后，迁移目标数据源再往同一张表插同 id，触发 `Duplicate entry for PRIMARY`。

**修复**：双写前先判断「新旧库表是否相同」，相同则跳过二次写入（数据已由主库落到正确位置）。

### 2. 存量搬迁与双写数据重叠

**现象**：脚本搬迁存量时，双写期间已写入新库的数据会被重复插入，再次主键冲突。

**修复**：搬迁脚本用 `INSERT ... ON DUPLICATE KEY UPDATE` 做**幂等**，目标已存在则跳过。

### 3. 旧库残留清理（容易遗漏）

搬迁是「复制」，不是「移动」——`h%4>=2` 的数据搬去 db2/db3 后，db0/db1 里还有残留。必须显式清理旧库中「不再属于新路由」的数据，否则 db0/db1 数据量虚高。

## 实测结果

- 3000 条存量 + 50 条双写数据，迁移后 4 库分布 **766 / 764 / 758 / 762**（均匀）
- 总量 3050 条，校验**零不一致**
- 切读新库后，db2/db3 中的短码跳转 **302 正常**
- 双写失败日志 0 条

## 复现方式

```bash
# 1. 起应用（默认 2 库路由）
java -jar turbolink-1.0.0.jar

# 2. 生成存量数据
cd benchmark && java DataGen http://localhost:8080/api/shorten 50 3000 /tmp/g.txt

# 3. 开启双写
curl -X POST http://localhost:8080/api/migration/dual-write/on

# 4. 搬迁存量（幂等）+ 校验 + 清理
java -cp ".;mysql-connector-j.jar" MigrationScript root 123456

# 5. 切读新库 + 关双写
curl -X POST http://localhost:8080/api/migration/read-new/on
curl -X POST http://localhost:8080/api/migration/dual-write/off
```
