# TurboLink 压测方案与报告

## 一、测试目标

验证高并发短链系统在读写两条核心链路上的性能表现，量化缓存与分库分表的价值，并为简历提供可信数据。

## 二、测试环境

| 项 | 配置 |
|----|------|
| 机器 | 16 核 / 16GB（测试时可用内存约 3.5GB） |
| 应用 | JDK 24 + Spring Boot 3.2.5 + 内嵌 Tomcat，**单实例** |
| 存储 | MySQL 8.0（本地）+ Redis 5.0.14（本地） |
| 压测工具 | 自研零依赖 Java 工具 `benchmark/LoadTester.java`、`benchmark/DataGen.java`（基于 JDK HttpClient） |

> **重要说明**：应用、MySQL、Redis、压测客户端**同机运行**，共享 CPU/内存/磁盘，数据偏保守。生产环境多机会有更好表现。所有数字均为本机实测，非理论值。

## 三、压测工具与方法

```
benchmark/LoadTester.java   # 读路径压测：get/post/getlist 三种模式，输出 QPS/延迟分位
benchmark/DataGen.java      # 写路径压测 + 数据生成：并发 POST，输出写 QPS
```

- **预热**：每次正式压测前先跑预热阶段，避免 JIT 未编译、连接未建立导致的数据失真。
- **延迟分位**：记录每个请求的纳秒级耗时，输出 P50/P90/P95/P99/P999，而非只看平均值——**P99 才反映真实用户体验**。
- **getlist 模式**：所有线程共享游标，每个 URL 只读一次，用于制造「缓存未命中」的冷读场景。

## 四、测试结果

### 4.1 写路径 `POST /api/shorten`（同步落库）

| 并发 | QPS | 平均延迟 | P99 |
|------|-----|---------|-----|
| 10 | 777 | 12.7ms | 28ms |
| 30 | 1073 | 27.6ms | 66ms |
| 50 | 1131 | 43.6ms | 284ms |
| 100 | 1428 | 68.4ms | 950ms |

**结论**：写路径受限于**同步 MySQL insert**，QPS 约 1.4K。这也是后续引入 MQ 异步化/批量写入的动机。

### 4.2 读路径 `GET /{code}`

**热读（缓存命中，单热点 key）**

| 并发 | QPS | 平均延迟 | P99 |
|------|-----|---------|-----|
| 10 | 23917 | 0.42ms | 1.96ms |
| **50** | **27821** | 1.79ms | 6.92ms |
| 100 | 22722 | 4.39ms | 15.8ms |
| 200 | 20333 | 9.82ms | 30.5ms |

**拐点在 50 并发**：超过后 QPS 反而下降、延迟飙升，典型的线程竞争/上下文切换过载特征。

**冷读（缓存未命中，穿透到 MySQL，2 万个不同 key）**

| 并发 | QPS | 平均延迟 |
|------|-----|---------|
| 10 | 7718 | 1.27ms |
| 50 | 7739 | 6.36ms |

### 4.3 关键对比

| 对比项 | 数值 | 说明 |
|--------|------|------|
| 读（缓存命中）vs 写 | **27.8K vs 1.4K ≈ 20×** | 短链是读多写少，读性能是核心 |
| 读（缓存命中）vs 读（穿透 DB） | **27.8K vs 7.7K ≈ 3.6×** | 缓存带来的读吞吐提升 |

### 4.4 接入 RocketMQ 异步统计后

跳转成功时异步投递访问事件（`asyncSend`，不阻塞 302 返回），消费者聚合 PV 落库。

| 场景 | QPS（50 并发） | 说明 |
|------|--------------|------|
| 跳转（无 MQ） | 27.8K | 纯读 |
| 跳转（+MQ 异步发送） | ~20K | 增加约 30% 开销，主链路仍不阻塞 |

**结论**：`asyncSend` 让 MQ 的网络耗时旁路到异步线程池，跳转仍保持约 2 万 QPS；PV 统计在消费者侧异步累加（实测 `pv` 随压测持续增长至数万），实现了「统计不影响主链路」。

## 五、压测暴露并修复的 4 个真实问题

这是压测最大的价值——**单元测试全部通过，但真实运行暴露了 4 个严重 bug**：

| # | 问题 | 现象 | 根因 | 修复 |
|---|------|------|------|------|
| 1 | **号段复用** | 并发下 `Duplicate entry`，账号段连续短码重复 | 预取任务提交与赋值之间存在竞态窗口，导致 current 与 next 指向同一号段 | 预取赋值收敛到 `switchLock` 内，并在锁内判重 |
| 2 | **过度取号** | 取号段数是理论值的 19 倍 | 预取任务先提交后判重，即使"该丢弃"也已浪费一次 DB 取号 | 先判重后提交 |
| 3 | **短码唯一键误冲突** | 同一 ID 报重复，且完全确定性 | `short_code` 列排序规则为 `utf8mb4_0900_ai_ci`（大小写不敏感），Base62 的 `1a` 与 `1A` 被判为同一值 | 改列为 `utf8mb4_bin`（区分大小写） |
| 4 | **布隆未预热** | 重启/Redis 清空后，所有存量短码跳转 404 | 布隆只增不建，重启后为空 | 新增 `BloomWarmUpRunner`，启动时游标分页回填全量短码 |

> **问题 3 尤其典型**：1..2000 范围内大小写折叠恰好产生 **832 个冲突**，与实测重复数**完全吻合**。这类问题单测（不碰真实 DB 排序规则）无法发现，**只有真实联调/压测能暴露**。

## 六、简历写法（可直接用）

```
TurboLink 高并发短链系统（Spring Boot + MySQL + Redis + Redisson + RocketMQ）
- 自研零依赖压测工具，实测读路径缓存命中峰值 2.7 万 QPS / P99 6.9ms，
  较未命中穿透 DB（7.7K QPS）提升约 3.6 倍
- 号段模式发号器（双缓冲预取 + DB 乐观锁），并发取号零重复、无锁化
- 三级缓存读路径（Caffeine + Redis + 布隆过滤器 + 互斥锁），
  分别解决命中率、穿透、击穿
- RocketMQ 异步解耦访问统计，asyncSend 旁路统计耗时，跳转主链路仍保持约 2 万 QPS
- 通过压测发现并修复号段复用竞态、短码列排序规则误冲突、
  布隆重启未预热等 4 个生产级缺陷
```

## 七、复现方式

```bash
# 1. 确保 Redis、MySQL 已启动，应用已运行在 8080
# 2. 编译压测工具
cd benchmark && javac LoadTester.java DataGen.java

# 3. 写路径压测（同时生成数据）
java DataGen http://localhost:8080/api/shorten 50 20000 /tmp/codes.txt

# 4. 读路径 · 缓存命中
java LoadTester http://localhost:8080/1 get 50 10 2

# 5. 读路径 · 冷读穿透（先清 url 缓存）
java LoadTester urls.txt getlist 50 60
```
